# 乐小读独立 AI 顾问与原文档直读架构设计

- 日期：2026-08-09
- 状态：已完成补充方案讨论，待业务方复审更新规格
- 适用范围：乐小读桌面端顾问辅助流程

## 1. 背景

乐小读当前采用悬浮工具栏和一次性建议窗口，流程是“识别家长顾虑 → 检索本地知识 → 取出匹配知识 → 豆包参照知识生成回复”。该流程将本地知识检索置于核心位置，豆包主要承担表达和组织工作；界面也更像截图、检索和回复生成工具，而不是顾问可以持续交流的 AI。知识导入又需要经过 Office/PDF 提取、图片 OCR、质量筛选、语义标记和权限门槛，任何提取失真或筛选遗漏都会让模型在回答时失去原始上下文。

新的业务目标是把乐小读变成类似豆包、ChatGPT 的独立桌面聊天应用，并让豆包成为顾问判断主体。顾问只需在独立会话中描述家长情况和自己的顾虑；乐小读通过多轮对话理解问题、主动追问、判断沟通策略，并结合公司原始文档形成有公司立场的回复。课程、师资、价格、政策等公司专属事实仍须以公司资料为准；通用教育判断和沟通策略可以由模型自主完成。回复继续由真人顾问确认、修改后发送。

业务方接受将选中的完整原文件上传至火山方舟，由方舟在云端解析；乐小读本地不再以 OCR、切块或知识抽取结果作为回答事实的唯一入口。

## 2. 目标

1. 豆包先理解对话和决定沟通策略，再按需读取公司原始文档。
2. 用独立主窗口取代悬浮工具栏，提供会话列表、连续聊天、附件输入和按需展开的引用/风险抽屉。
3. 每个会话拥有独立且可在应用重启后恢复的本地上下文，不能跨会话串用家长信息。
4. PDF、PPT/PPTX、Word/DOCX 等原件在乐小读本地不做内容改写、OCR、切块或事实筛选。
5. 本地自动选择最多三份候选原件；选择不确定时由顾问确认、增删或替换。
6. 公司专属事实必须绑定原文件及页码、幻灯片或章节位置；无法定位的事实不得进入可复制回复。
7. 保留本地确定性风险规则和真人发送门槛。
8. 在本地形成脱敏、人工审核、版本化发布的学习闭环，不允许系统在线自行改变规则。
9. 通过文档路由、事实可定位率、顾问采用率和安全指标证明新方案优于当前版本。

## 3. 非目标

1. 首期不让 AI 直接向家长自动发送消息。
2. 首期不训练或微调专属模型。
3. 不把顾问案例中的课程、价格、师资、政策或效果描述当作当前公司事实。
4. 不从静态文档推断实时名额、订单、付款或 App 显示状态。
5. 不删除、覆盖或迁移现有本地知识库和已审核来源数据。
6. 不在首期接入无边界的公司网络抓取；只处理明确登记、授权的文件目录和文件。
7. 首期不提供跨电脑、跨账号或公司服务器的聊天记录同步。
8. 不建立跨会话的家长画像或自动长期记忆；上下文只能在当前会话内使用。

## 4. 已确认的产品决策

### 4.1 AI 判断权限

采用分层权限：豆包可以使用通用教育常识和顾问经验分析家长顾虑、给出判断、追问和沟通建议；公司产品、价格、课程、师资、政策等专属事实必须来自授权原文件。通用认知与公司资料冲突时，以公司资料为准。

### 4.2 发送权限

首期定位为顾问助手。AI 生成草稿，真人顾问查看引用、修改并复制发送。高风险场景继续要求显式确认或转人工。

### 4.3 原文件处理边界

乐小读不对原文件正文进行本地 OCR、切块、脱敏或知识抽取。原文件保持不变，以文件哈希识别版本。选中的完整文件可以上传火山方舟，由方舟在云端完成其所需的解析。这里的“不处理”是指乐小读不改变或派生正文，不代表云端模型无需解析二进制文件。

该边界只适用于公司资料读取；家长聊天截图仍可沿用现有本地 OCR 和顾问校正流程，因为它属于对话输入而不是公司知识加工。

### 4.4 文档选择方式

采用“自动选择 + 低置信人工确认”：正常情况下本地自动选择一至三份原文件；置信不足时展示候选文件名、版本和选择理由，由顾问确认或换文件。

### 4.5 学习方式

本地保存脱敏后的问题场景、AI 初稿、顾问终稿、采用动作和反馈原因。所有学习候选必须经过人工审核才能进入优秀案例、公司立场、文档路由标签或失败评测集；任何资产变更均版本化、可回滚。

### 4.6 独立聊天应用

乐小读启动后直接进入完整主窗口，不再以悬浮工具栏作为主要入口。界面采用聊天优先布局：左侧显示新建聊天、搜索和本地历史会话；中间显示顾问与乐小读的连续对话；公司原文件、引用、风险和当前会话信息通过右侧抽屉按需展开。

### 4.7 回复生成时机

采用混合模式。乐小读平时像真人顾问一样与顾问讨论、追问和分析；信息充分时主动提示可以整理回复。只有顾问确认、点击生成动作或明确提出“帮我整理回复”后，才生成可编辑、可复制的家长回复卡。

### 4.8 会话持久化与隔离

首期聊天记录只保存在当前电脑，不跨设备同步。每个会话拥有独立消息、摘要、已确认事实、附件、文档引用和生成记录。应用关闭或电脑重启后可以继续原会话；新建会话从空上下文开始，任何检索和记忆都必须带当前会话 ID。

### 4.9 长上下文策略

完整原消息在本地保留。每轮实际发送给豆包的上下文包由“已确认事实、可重新生成的历史摘要、最近对话和从当前线程按需取回的相关旧消息”组成。历史摘要不是唯一真相，必须记录覆盖的消息范围和生成版本，并可从原消息重新生成。

### 4.10 截图附件

截图和粘贴图片成为聊天输入框中的附件能力，不再依赖悬浮工具栏。原图使用本地加密存储并显示缩略图；顾问校正后的 OCR 文字进入当前会话上下文。原图默认不上传方舟。删除会话时，同时删除原图、校正文字、上下文摘要和未审核学习候选。

## 5. 总体架构

系统由十二个边界清晰的组件组成。

### 5.1 Independent Chat Shell（独立聊天主窗口）

主窗口采用聊天优先布局：

- 左侧栏：新建聊天、本地搜索、自动标题、手动重命名、历史会话列表和删除；
- 中间区：顾问消息、乐小读消息、附件、工具状态和正式回复卡；
- 顶部栏：当前会话标题、本地保存状态和引用/风险抽屉入口；
- 输入区：多行文字、截图、粘贴图片、发送和失败消息重试；
- 右侧抽屉：当前会话已确认事实、候选公司文件、引用、待确认项和风险结果。

工具运行状态以简短的会话事件显示，例如“正在选择公司资料”“正在读取 2 份原文件”，不暴露内部提示词、模型思维链或技术堆栈。

### 5.2 Conversation Repository（会话仓库）

负责本机持久化和严格线程隔离。核心记录包括：

- `conversation`：会话 ID、标题、创建/更新时间、状态和上下文版本；
- `message`：消息 ID、会话 ID、角色、类型、正文、发送状态、时间和模型元数据；
- `confirmed_fact`：顾问或模型在当前线程中确认的孩子年级、学科、顾虑等事实及来源消息；
- `context_summary`：摘要文本、覆盖消息范围、生成模型和版本；
- `document_usage`：本轮候选文档、顾问确认结果、文件哈希和引用；
- `generation_record`：AI 初稿、正式回复卡、顾问终稿、风险和反馈。

所有读取和写入接口都必须显式接收会话 ID。新建会话不能复制上一会话的摘要、已确认事实、附件或文档选择。

会话搜索由当前 Windows 用户进程解密标题和消息后执行，首期不建立明文全文索引。搜索结果只返回匹配会话，不形成可被其他进程直接读取的消息副本。

### 5.3 Encrypted Attachment Store and OCR（加密附件与 OCR）

截图和粘贴图片使用随机附件 ID 保存在应用专用目录，文件名不包含家长或学员信息。附件内容使用本地随机数据密钥加密，该密钥由 Windows 当前用户范围的 DPAPI 保护。数据库只保存附件 ID、会话 ID、哈希、尺寸、加密路径、OCR 状态和缩略图信息。

截图仍使用现有本地 OCR，识别后必须让顾问校正。原图和校正文字都属于当前会话；默认只把校正文字加入豆包上下文，原图不上传方舟。删除会话时级联删除附件、OCR 校正、缩略图、摘要和未审核学习候选。

### 5.4 Context Builder（上下文构建器）

完整消息历史始终保存在本地。Context Builder 根据模型上下文预算构造每轮输入：

1. 当前线程已确认事实；
2. 覆盖较早消息的可再生摘要；
3. 最近对话；
4. 从当前线程旧消息中按需取回的相关内容；
5. 本轮附件校正文字、文档选择和工具结果。

摘要必须记录起止消息 ID 和生成版本。修改或删除被摘要覆盖的消息后，旧摘要立即失效并重新生成。旧消息检索只能在当前会话 ID 范围内执行，不建设跨会话长期记忆。

### 5.5 Advisor Planner（顾问判断器）

由豆包基于 Context Builder 的上下文包输出结构化结论：

- 家长表层问题；
- 真实顾虑；
- 当前沟通阶段；
- 本轮目标；
- 应直接讨论、追问还是建议整理回复；
- 需要核实的公司事实类型；
- 用于本地文档路由的检索目标。

系统不要求、不保存也不展示模型内部思维链，只消费上述可验证的结构化结论。Planner 只能提示“可以整理回复”，不能绕过顾问确认直接创建正式回复卡。

### 5.6 Local Document Catalog（本地文档目录）

目录只维护选文档所需的文件级元数据，不解析正文。每条记录至少包含：

- 稳定文档 ID；
- 本地绝对路径和显示名称；
- 文件格式；
- 文件哈希、大小和修改时间；
- 业务分类、年级、学科、班型和时期等人工标签；
- 版本状态与权威等级；
- 是否允许上传方舟；
- 允许使用的顾问角色；
- 已上传的方舟文件标识及其对应哈希；
- 最近上传状态和审计时间。

旧文件版本不物理删除，但不能被自动选择为当前事实来源。

### 5.7 Local Document Router（本地文档路由器）

路由器接收 Advisor Planner 的检索目标，从文件名、目录、人工标签、版本元数据以及现有轻量索引信号中选择候选原件。现有本地知识库可以提供“可能是哪份文档”的弱信号，但不再作为最终回答事实的唯一权威。

路由结果包含候选文档、选择理由和置信等级：

- 高置信：自动选择一至三份原件并继续；
- 中置信：在会话内显示候选，由顾问一键确认、增删或替换；
- 低置信或无候选：只追问一个最关键的信息，或者打开本地文件选择器，不生成无依据公司事实。

候选数量默认最多三份，避免把大量无关原件上传给模型。数量限制可以通过评测调整，但首期不开放为普通用户配置项。

### 5.8 Ark Original File Gateway（方舟原文件网关）

网关隐藏具体方舟接口差异，职责是：

1. 在上传前检查文档权限、版本和文件哈希；
2. 相同哈希优先复用仍有效的方舟文件标识；
3. 上传完整原文件，不在本地改写正文；
4. 记录文档、会话、顾问、方舟文件标识、模型和时间的审计事件；
5. 对短暂失败重试一次，避免无界重试；
6. 在文件版本变化后使旧的方舟文件映射失效。

实现前必须用当前启用的方舟端点验证 PDF、DOCX 和 PPTX 原件输入能力。旧版 DOC 和 PPT 仅在当前方舟端点明确支持时放行，不能为了兼容而在本地静默转换。若 File API 对某种格式不直接支持，网关应改用方舟官方知识库的原文档上传能力；仍不得在乐小读本地转换正文。若当前账户和端点均不支持某格式，该格式在首期显示为不支持并转为人工处理，不得静默遗漏。

### 5.9 Original Document Advisor Generator（原文档顾问生成器）

普通对话轮次返回自然的顾问分析、追问或建议，不强制创建回复卡。顾问确认整理回复后，生成器接收当前上下文、Advisor Planner 结论、选中的方舟文件以及版本化的公司立场和脱敏优秀案例，并返回固定结构：

- `concern_summary`：给顾问看的顾虑摘要；
- `strategy_summary`：本轮沟通策略；
- `wechat_reply`：可编辑微信回复；
- `company_claims`：公司事实列表；
- `general_judgments`：通用教育判断列表；
- `needs_confirmation`：原文未覆盖、读取不清或存在冲突的事项；
- `follow_up_question`：仅在信息不足时返回的一个关键追问。

每条 `company_claim` 必须包含事实文本、文档 ID、文档显示名称、页码/幻灯片/章节定位和模型给出的证据片段。优秀案例只能影响策略和语气，不能进入 `company_claims`。

### 5.10 Evidence Validator and Risk Guard（证据与风险校验）

本地校验层不依赖模型自律，执行以下硬规则：

- 公司事实缺少有效文档和定位时，从可复制回复中移除，并放入待确认提醒；
- 多份当前原文冲突时，优先已审核、较新和较高权威版本；仍无法消解则展示冲突，不自动选择结论；
- 实时业务状态不得由文档回答；
- 投诉、退费、法律、人身安全、隐私和儿童保护继续应用确定性风险规则；
- 模型返回格式无效时不展示半结构化草稿，转为可重试错误；
- 通用教育判断可以不引用公司文件，但不得伪装成公司制度、产品承诺或确定效果。

### 5.11 Reply Card and Human Review（回复卡与人工确认）

正式回复卡只在顾问明确确认后出现，包含可编辑微信回复、公司事实引用、待确认事项、风险提示、换文档重答和复制操作。顾问可以继续在同一会话中追问或修改需求，生成的新回复卡以新版本保存，不覆盖旧记录。

### 5.12 Learning Pipeline（学习管线）

学习事件在本地生成，包含模型与提示词版本、选中文档 ID 和哈希、AI 初稿、顾问终稿、采用动作、反馈原因、风险标记和引用校验结果。事件写入学习库前先执行确定性脱敏；原始姓名、手机号、微信号、订单号、学员号和员工标识不得进入学习库。

## 6. 端到端数据流

1. 顾问启动乐小读，进入最近会话或新建空白会话。
2. 顾问输入文字、截图或粘贴图片；截图先在本地 OCR 并由顾问校正。
3. Conversation Repository 在调用豆包前先持久化顾问消息和附件引用，并标记为待处理。
4. Context Builder 从当前会话构造“已确认事实、历史摘要、最近消息和相关旧消息”的上下文包。
5. Advisor Planner 返回顾虑判断、追问或文档检索目标，乐小读在聊天中自然回应。
6. 如果信息不足，乐小读只追问一个最关键的问题；如果信息充分，提示顾问可以整理回复。
7. 顾问确认整理回复后，Local Document Router 返回最多三份候选及置信等级。
8. 高置信直接继续；中低置信在会话内由顾问确认、换文件或补充一个关键信息。
9. Ark Original File Gateway 检查权限和版本，上传原件或复用文件标识。
10. Original Document Advisor Generator 读取原件，结合公司立场和脱敏案例形成结构化回复卡草稿。
11. Evidence Validator 校验每条公司事实的位置和版本，Risk Guard 计算本地风险结果。
12. Conversation Repository 原子保存 AI 消息、回复卡、引用、风险、上下文版本和完成状态，再更新界面。
13. 顾问查看引用、修改并复制回复；后续追问继续留在同一线程，新回复卡按版本追加。
14. 系统在本地对问题、初稿和终稿脱敏，写入学习候选队列。
15. 审核人员决定候选进入优秀案例、公司立场、路由标签、失败评测集或拒绝集合。
16. 新资产通过离线评测后版本化发布；失败时继续使用上一版本。

## 7. 公司立场与优秀案例

### 7.1 公司立场

公司立场是经业务负责人审核的稳定判断原则，例如如何看待班型选择、学习效果、续报顾虑和家长异议。它不等于产品事实，也不能覆盖原文档中的明确规则。立场资产必须有版本、审批人角色、启用时间和适用场景。

### 7.2 优秀案例

优秀案例只保存脱敏场景、家长真实顾虑、顾问策略、有效追问和建议回复。案例中的价格、优惠、教师经历、课程参数和政策不得成为事实证据。案例审核重点是“为什么这次沟通有效”和“哪些表达可以复用”，而不是原样复制个人口癖。

### 7.3 晋级规则

- 顾问复制不等于自动晋级；
- 顾问终稿必须完成人工审核；
- 公司立场变更需要高于普通案例审核的业务审批；
- 失败样例优先进入评测集，而不是直接生成新规则；
- 线上提示词、案例库和立场库均有独立版本，支持单独回滚。

## 8. 隐私、安全与外部数据边界

业务方已接受完整原件上传方舟，因此首期采用文件级权限控制而不是本地正文脱敏。该决策带来明确边界：只要文件被允许上传，文件内全部内容都可能由方舟云端处理。上线前必须确认公司与供应商的数据处理约定、账户权限、保存期限和审计要求。

本地文档目录必须默认拒绝上传，只有明确设置为允许的文件或目录才能进入网关。顾问聊天截图、真实学员材料、员工联系方式和其他受限资料不能仅凭文件名自动放行。文件权限由业务管理员维护，普通顾问不能自行扩大可上传范围。

聊天数据库中的消息正文、上下文摘要、已确认事实和生成记录使用应用层加密；截图原图、缩略图和其他附件使用独立加密文件。随机数据密钥由 Windows 当前用户范围的 DPAPI 保护，其他 Windows 用户不能直接解密。首期不提供云备份或跨设备密钥恢复；Windows 用户配置丢失可能导致本地历史不可恢复，产品需在设置页明确提示。

首期以 Windows 用户配置作为本地数据边界，不新增公司账号系统。同一 Windows 账号下运行乐小读的人员能够看到同一份本地会话，因此共享电脑必须为不同顾问使用不同 Windows 账号。

每个上下文构建、旧消息检索、附件读取和文档使用查询都必须同时带当前会话 ID。自动化测试必须证明不同会话即使出现相同年级、学科或关键词，也不会互相返回消息、摘要、附件或公司文件选择。

截图原图默认只保存在本地，不上传方舟；顾问校正后的 OCR 文字会作为当前会话相关上下文发送给豆包。完整聊天虽然本地持久化，但实际参与当前回答的上下文包会离开本机，因此上线前同样需要确认顾问聊天数据的供应商处理边界。

学习库与方舟原文件上传是两个独立边界：允许原文件临时用于回答，不代表允许其聊天内容、个人信息或模型输出进入长期学习资产。删除会话时必须删除原消息、附件、摘要、生成记录和未审核学习候选；已经完成脱敏并经人工批准的独立学习资产不包含会话标识，不受会话删除影响。

## 9. 异常处理

### 9.1 没有候选文档

系统优先提出一个能够显著缩小范围的问题，例如年级、学科或班型；顾问也可以直接选择文件。系统可以提供通用沟通建议，但不能给出公司专属事实。

### 9.2 选错文档

顾问可查看候选文件和引用，一键移除错误文档、补选文件并重新生成。该事件进入文档路由失败评测集。

### 9.3 原文没有答案

AI 可以继续分析顾虑并给出通用教育建议；公司专属部分进入 `needs_confirmation`，回复中使用自然的确认表达，不解释内部检索或系统状态。

### 9.4 原文冲突

系统按已审核状态、版本时间和权威等级排序。无法确定时不合并冲突事实，向顾问展示冲突文件与位置，并要求人工决定。

### 9.5 上传或方舟读取失败

网关先尝试复用已有文件标识，再进行一次短暂重试。仍失败时保存当前问题、候选文件和错误分类，允许顾问稍后重试；不得自动退回可能过时的本地片段并伪装成同等结果。

### 9.6 引用无法定位

对应公司事实不得进入可复制回复。通用判断和不依赖该事实的回复部分仍可保留。

### 9.7 消息发送或应用中断

顾问消息必须先本地保存再发起网络请求。网络失败时消息保留并标记为失败，顾问可原位重试。重试使用同一请求 ID，防止恢复后生成两条重复 AI 回复。应用重新启动时，所有未完成请求显示为可重试，不自动在后台发送。

### 9.8 上下文摘要失败或失效

摘要生成失败不影响原消息。Context Builder 临时使用最近对话和可容纳的旧消息继续运行，并在后台可重试摘要。被摘要覆盖的消息发生修改或删除后，旧摘要立即失效，不能继续发送给豆包。

### 9.9 附件损坏或无法解密

损坏附件显示明确错误并保留对应消息文字；不能把空附件当作已识别内容。附件无法解密时不上传、不 OCR，也不删除其他会话数据。

### 9.10 删除会话失败

删除操作在一个本地事务中标记会话不可见，并完成消息、附件、摘要和未审核学习候选清理。附件文件清理失败时记录待清理任务并重试，不能让已删除会话重新出现在列表中。

## 10. 测试与评测

### 10.1 单元测试

- 会话创建、搜索、重命名、删除和重启恢复；
- 消息保存先于网络调用、失败重试和请求幂等；
- 会话 ID 强制过滤与跨会话隔离；
- 摘要覆盖范围、失效和从原消息重新生成；
- 附件加密、DPAPI 密钥保护、OCR 校正和级联删除；
- 文档目录的版本、权限、哈希和方舟文件映射；
- 高、中、低置信文档路由分支；
- 生成请求和响应结构校验；
- 公司事实引用缺失、文档冲突和实时状态阻断；
- 本地脱敏和学习资产晋级权限；
- 风险规则与复制确认。

### 10.2 集成测试

- 标准启动直接显示独立聊天主窗口，不出现悬浮工具栏作为主入口；
- 会话侧栏、消息区、截图输入、回复卡和引用/风险抽屉的关键交互；
- 关闭并重新启动应用后恢复历史会话、消息、附件和回复卡；
- 长对话压缩后仍能正确使用已确认事实，并能按需找回旧消息；
- 两个包含相似内容的会话不会互相污染上下文；
- 截图在输入框添加、OCR 校正、重启恢复和删除会话后的完整生命周期；
- 使用模拟方舟网关验证上传、复用、失效和一次重试；
- 使用代表性 PDF、DOCX、PPTX 验证实际方舟端点兼容性；
- 验证文件不受本地修改，上传哈希与目录记录一致；
- 验证多轮对话能够影响文档选择和回复策略；
- 验证顾问换文档后重新生成不会混用旧引用。

### 10.3 匿名真实评测集

建立至少 100 条经脱敏、人工标注的真实问题。每条记录包含预期原文件、必要事实、允许的通用判断、禁止表述、是否需要业务系统以及期望动作。不能再以“检索到任意事实”作为通过条件。

### 10.4 首期验收线

- 敏感信息泄漏、无依据公司事实和高风险规则绕过：评测集中均为 0；
- 跨会话消息、摘要、附件和事实泄漏：自动化隔离测试中均为 0；
- 正常关闭、异常退出和电脑重启后的会话恢复成功率：测试场景中为 100%；
- 长会话已确认事实保持率：不低于 95%；
- 文档路由 Recall@3：不低于 90%；
- 对客公司事实可定位率：不低于 95%；
- 顾问直接采用或仅轻量修改的比例：不低于 70%；
- 低置信或原文缺失时的错误自动回答率：不高于 2%；
- 使用同一匿名评测集对新旧版本做 A/B，对事实质量、顾问评分、采用率和响应时间分别报告，不以单一综合分掩盖安全退化。

先用现有版本跑出基线。安全硬门槛必须全部满足；新方案还必须在文档路由和顾问采用率上优于当前版本，才允许扩大试点。

## 11. 分阶段交付

### 阶段一：独立聊天壳与本地会话

建立聊天优先主窗口、会话列表、消息区、输入区、右侧抽屉、Conversation Repository 和本地加密。实现新建、搜索、重命名、删除、重启恢复、失败重试和线程隔离；暂时使用模拟 AI，不改变方舟链路。

### 阶段二：截图附件与长上下文

把现有截图/OCR能力迁入聊天输入框，加入加密附件存储、顾问校正、Context Builder、摘要失效和当前线程旧消息取回。

### 阶段三：方舟原文件能力验证

选取包含文本、表格、图片和扫描页的代表性 PDF、DOCX、PPTX，验证当前账户和端点的原文件输入、定位质量、响应时间、文件复用和数据保存策略。该阶段只形成技术报告，不改变生产链路。

### 阶段四：本地文档目录与路由

建立文件级目录、权限、版本和人工标签；实现高置信自动选择与中低置信人工确认。现有本地知识索引只作为可选路由信号。

### 阶段五：原文件网关与 AI 顾问生成

接入方舟文件能力，把既有多轮上下文接入 Advisor Planner、结构化回答契约、引用校验和错误处理。通过功能开关与现有流程并行，不立即删除旧链路。

### 阶段六：顾问试点与学习闭环

小范围顾问试用，收集脱敏初稿、终稿和反馈；建立人工审核、案例晋级、失败评测和版本回滚。

### 阶段七：评测与扩展

完成至少 100 条匿名真实问题的 A/B 评测。达到验收线后扩大试点；积累足够高质量样例后，再单独评估模型微调，不把微调纳入本设计首期。

## 12. 现有系统迁移策略

1. 保留当前知识库、来源审核数据和风险规则，不做破坏性迁移。
2. 应用启动入口改为独立聊天主窗口；现有悬浮工具栏不再作为主产品形态。旧工具栏代码在迁移期保留在功能开关后，不立即删除。
3. 将现有内存聊天记录迁移为 Conversation Repository；新版本启用前产生的旧进程内聊天没有可迁移数据。
4. 将截图选择、OCR 和文字校正迁入聊天输入框附件流程，复用识别能力但替换悬浮触发和一次性建议窗口编排。
5. 将现有 `AdviceService` 的“检索后生成”改造目标拆为上下文构建、顾问规划、文档路由、原件网关、生成、证据校验六个独立边界。
6. 现有本地知识检索可以在过渡期提供文件级路由信号，但不能继续决定 AI 的全部回答能力。
7. 现有可编辑回复、引用展示、风险确认和反馈组件改为聊天内回复卡和按需抽屉，业务规则优先复用。
8. 新旧流程通过功能开关并存，试点失败可立即回到旧流程。
9. 不在迁移中清理旧知识文件、SQLite 数据、OCR 缓存或审核批次；后续是否退役另立任务和审批。

## 13. 实施前置条件

进入实施计划前必须具备：

1. 可用于技术验证的代表性 PDF、DOCX、PPTX 样本；
2. 火山方舟测试环境、模型端点和文件能力权限；
3. 公司批准上传方舟的文件目录或文件白名单；
4. 文档业务分类、当前版本和权威等级的维护责任人；
5. 首批匿名真实问题和预期原文件标注人；
6. 优秀顾问样例的脱敏与审核责任人。
7. 本机聊天记录保存期限、删除责任和 Windows 用户配置丢失后的数据处置说明；
8. 允许发送给豆包的顾问聊天上下文和截图 OCR 文字范围。
9. 共享电脑为不同顾问分配独立 Windows 账号的使用规则。
